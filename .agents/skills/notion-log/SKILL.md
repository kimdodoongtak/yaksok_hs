# Notion 개발 기록

이 스킬은 혜승의 **약속 잡기 도우미** 개발 과정만 기록한다. 사용 예: `$notion-log 티켓 000`, `$notion-log 결정 OPEN-01`. 기능 구현·검증이나 Git 커밋은 이 스킬의 작업이 아니다. 모든 기록은 한국어로 쓴다.

## 기록 위치

- 연결된 Notion에서 `🖤💗 약속 잡기 | 혜승 개발 기록` 홈을 찾고, 하위의 `🖤 구현 티켓`과 `💗 결정 기록` 데이터베이스를 사용한다. 제목만 같은 다른 공간이 있으면 데이터베이스 이름과 스키마까지 대조한다.
- 기존 페이지가 있으면 갱신한다. 홈·데이터베이스·동일 ID 카드의 복제본을 만들지 않는다. 대상이 없거나 여러 개라 확정할 수 없으면 링크를 요청한다.
- Notion 도구가 없거나 접근이 안 되면 실제 기록했다고 말하지 말고, 붙여 넣을 한국어 초안을 제공한다.

## 근거 확인

- 티켓은 `context/current-feature.md`, 해당 `context/features/` 스펙, 존재하는 `context/tdd/<스펙-ID>.md`, 실제 검증 기록과 관련 변경을 읽는다. Git 저장소가 있을 때만 커밋·변경 내역을 근거로 사용한다.
- 결정은 `context/spec-plan.md`의 OPEN 항목, 해당 스펙과 대화에서 사용자가 확정한 내용을 대조한다. PRD·ERD 충돌은 사용자 결정에 따라 ERD를 우선한다.
- 계획, 제안, 구현, 실행된 검증을 구분한다. 실행하지 않은 RED·GREEN이나 테스트를 통과로 기록하지 않는다.

## 티켓 기록

1. Notion의 `🖤 구현 티켓`에서 `스펙 ID`로 기존 카드를 찾는다. 같은 ID가 없을 때만 새 카드를 만든다. 기존 사용자의 메모와 결정 링크는 보존한다.
2. 목표·사용 자료를 짧게 적고, **구현 접근과 선택 이유**, 비교할 만한 대안, 스펙과 달라진 부분, 핵심 예외를 중심으로 요약한다. 파일별 변경 목록은 필요할 때만 근거 링크로 둔다.
3. TDD 대상이면 실제 RED → GREEN → REFACTOR의 대표 동작과 실행 결과를 기록한다. 비대상이면 그 이유와 실제 대체 검증을 기록한다. 실패·미검증·남은 위험은 그대로 드러낸다.
4. 카드 상태는 근거에 맞춰 `백로그`·`진행 중`·`검증 중`·`완료` 중 하나로 갱신한다. `완료`는 로컬 기능 완료 이력과 필수 검증 근거가 있을 때만 사용한다. 시작일·완료일은 확인된 날짜만 입력한다.

## 결정 기록

1. `💗 결정 기록`에서 `결정 ID`로 기존 카드를 찾아 갱신하거나 새 카드를 만든다. 질문·필요 시점·근거·검토한 해법을 적고 영향을 받는 티켓을 관계 속성으로 연결한다.
2. 명시적으로 확정되지 않은 해법은 `결정 필요` 또는 `검토 중`으로 둔다. 확정되면 선택한 해법, 이유, 결정 근거, 스펙·테스트에 반영된 결과를 적는다. 제안을 승인된 정책으로 바꾸지 않는다.
3. 로컬 스펙과 결정이 어긋나면 조용히 덮어쓰지 말고 차이를 보고한다.

Notion에 쓰기 전에 대상 페이지와 데이터베이스를 읽고, 도구가 요구하는 Markdown·스키마 형식을 확인한다. 끝나면 갱신한 카드 링크와 미검증 사항을 짧게 알린다.
