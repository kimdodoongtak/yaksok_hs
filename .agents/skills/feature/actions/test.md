# 검증 — TDD 근거와 회귀 확인

현재 기능, 연결된 스펙, 기능별 TDD 기록, `context/tdd-policy.md`를 읽는다.

- 이 단계는 구현 중 수행한 RED·GREEN의 증거 확인과 최종 회귀 검증이다. TDD를 처음 시작하는 사후 테스트 단계로 사용하지 않는다.
- AC와 원본 규칙, 테스트 기대값이 일치하는지 대조한다. 새 제품 동작이 빠졌다면 해당 동작부터 RED → GREEN → REFACTOR로 보완한다.
- 이미 구현된 동작에 테스트를 추가한다면 사후 테스트라고 명시한다. 기록이 없는 과거 실패를 만들거나 소급해 TDD 통과로 표시하지 않는다.
- 테스트가 있으면 `npm run test`를 실행한다. 없으면 '테스트 없음'과 비대상 근거를 기록한다. 필수 대상 테스트가 없으면 미충족이다. 빈 테스트 성공 옵션을 추가하지 않는다.
- 단순 CSS·정적 화면에는 의미 없는 테스트를 추가하지 않고 브라우저에서 실제 결과를 확인한다.
- 앱 소스가 있으면 `npm run lint`, `npm run typecheck`, `npm run build`를 실행한다. 아직 소스가 없는 템플릿의 앱 빌드 통과를 주장하지 않는다.
- DB 변경에는 격리된 테스트 DB의 마이그레이션·실제 연결·필요한 제약/동시성 검증을 포함한다. DB 대역 통과만으로 실제 트랜잭션 검증을 대체하지 않는다.
- UI 변경은 사용자 흐름·오류·반응형·필요한 Figma 비교를 수행한다. 자동 E2E가 필수라면 도구와 실행 명령을 스펙에 정의하고 실제로 실행한다.

명령은 프로젝트 루트에서 `docker compose exec tools`를 앞에 붙인다. `tools`의 위치는 `/workspace/apps/web`이다. 특정 테스트는 `npm run test -- <실제 파일 경로> -t "<실제 테스트 이름>"`로 실행한다. 호스트 npm은 `apps/web/`에서만 사용한다.

기능별 TDD 기록에 실제 명령·종료 코드·핵심 결과·미실행 이유를 남기고 `current-feature.md`에는 요약과 기록 경로를 연결한다. 실패 수정 후 영향을 받는 검증을 다시 수행한다.
