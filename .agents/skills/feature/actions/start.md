# 구현 시작 — TDD

현재 기능, 연결된 스펙, `context/tdd-policy.md`를 읽는다. 목표가 비어 있으면 기능을 먼저 불러온다. 실제 선행 작업과 구현을 막는 미정 사항을 확인하되 이미 확정된 범위를 반복 확인하지 않는다.

1. 프로젝트 위치, Git 상태·브랜치·HEAD와 기존 사용자 변경을 기록한다. Git이 아직 초기화되지 않았으면 그 사실을 기록하고 Git 작업을 하지 않는다. `main` 전용 규칙은 Git 저장소일 때 적용하며 새 브랜치를 만들지 않는다.
2. 스펙의 TDD 범위·AC별 검증 방법을 확인한다. 비어 있으면 동작 기준으로 보완한다. 테스트할 공개 경계·기대값의 원본 근거·비대상 이유를 명시한다.
3. `context/tdd/<스펙-ID>.md`를 만들거나 이어 쓰고 현재 기능에 경로를 연결한다. 상태를 `진행 중`으로 바꾼다.
4. **TDD 대상 동작 하나씩** 테스트 작성 → 실제 실행과 의도한 실패 확인(RED) → 최소 구현 → 같은 테스트와 관련 회귀 테스트 통과(GREEN) → 필요한 코드 정리와 재실행(REFACTOR)을 반복한다. 정책 문서의 예외·실패 판정·DB 격리 기준을 따른다.
5. 비대상 변경은 이유를 기록하고 해당 변경에 맞는 실제 검증을 한다. 초기 앱 생성은 `000-project-bootstrap.md`를 따르며 가짜 제품 테스트를 만들지 않는다.
6. 개발 파일은 `apps/web/`에, 명세·진행·TDD 기록은 `context/`에 둔다. 검증은 Docker Node.js 24와 `docs/local-development.md`의 명령을 사용한다. DB 변경은 허용된 로컬 환경에서 마이그레이션으로 남긴다.
7. 변경 파일, 실제 검증 결과, 미충족 AC를 기록한다. 정책 결정이 바뀌면 근거와 함께 스펙을 동기화한다. 미검증 항목을 완료로 바꾸지 않는다.

사용자가 구현까지 요청한 범위는 이어서 수행한다. 커밋·푸시·외부 배포는 별도 요청 범위를 따른다. 환경 차단이 있으면 원인과 남은 검증을 보고하며 실행 결과를 추정하지 않는다.
