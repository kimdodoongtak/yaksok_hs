## 사용자와 문제

모임 주최자가 카카오 챗봇에서 초대 링크를 받아 웹의 방장 등록과 약속 조율을 시작한다.

## 목표와 범위

챗봇 진입 시나리오, 스킬 요청·응답 검증, 링크 발급 서비스 호출, 오류·재시도 안내, 실제 왕복 검증. 카카오 로그인·알림톡·확정 결과 자동 발송·그룹 채팅 내 상시 봇 동작은 자동으로 포함하지 않는다.

## 선행 작업

- [001-invitation-and-host](001-invitation-and-host-spec.md)

001의 링크 발급·읽기 서비스를 사용한다. 구현 순서는 전체 웹 검증 뒤를 제안하지만 실제 코드 의존성은 001뿐이다. 외부 가능 여부 검토는 초기부터 병행할 수 있다. AC-6의 전체 흐름 검증은 001~009의 웹 구현을 마친 뒤 수행하며, 그 전에는 010 완료로 처리하지 않는다.

## 사용자 흐름

지원되는 챗봇 진입 → 링크 발급 의도 → 스킬 호출 → 링크 응답 → 웹에서 명시적 방장 등록. 응답 실패는 재시도를 안내하며 자동 약속 선점이나 무거운 후보 계산을 하지 않는다.

## 수용 기준

- [ ] AC-1: 실제 지원되는 카카오 진입 방식과 스킬 요청·응답 JSON, 호출 검증 방법을 공식 문서·접근 가능한 테스트 환경으로 확인하고 스펙에 근거를 추가한다. PRD의 채팅방 초대 가정을 확인 없이 구현 사실로 쓰지 않는다.
- [ ] AC-2: 유효한 링크 발급 요청은 001을 통해 고유 초대 토큰을 발급하고 웹 링크를 반환한다. 이 단계에서는 약속·방장을 생성하지 않는다.
- [ ] AC-3: 잘못된 요청·검증 실패·호출 제한·DB 장애는 승인된 플랫폼 응답 계약에 맞는 오류나 복구 안내를 반환하고 비밀값을 노출하지 않는다.
- [ ] AC-4: 동일 요청 재전송의 링크 재사용 또는 새 발급 정책을 OPEN-13에서 결정하고 응답 유실·재시도 시나리오로 검증한다. 문서에 없는 이벤트 ID를 존재한다고 가정하지 않는다.
- [ ] AC-5: PRD의 스킬 응답 5초 요구를 목표로 링크 발급만 처리하고 실측한다. 실제 플랫폼 제한과 운영 환경 시간 제한은 공식 규격 확인 후 고정한다.
- [ ] AC-6: 실제 챗봇→링크→방장 등록→설정→참여→시간 제출→후보→수동 확정→공유의 MVP 흐름을 완료한다. 대역 테스트만으로 챗봇 연동 완료를 선언하지 않는다.

각 AC의 근거와 확인 방법은 아래 TDD 적용 계획에 대응한다. OPEN 항목이 포함된 AC는 해당 결정 전 완료 처리하지 않는다.

## 데이터와 인터페이스

POST /api/kakao/skill은 PRD가 제시한 경로를 사용하되 본문·응답·요청 검증·재시도 계약은 미정이다. Route Handler는 검증된 요청을 issueInviteLink 서비스로 전달한다. 외부 사용자 식별자를 전역 회원으로 자동 저장하지 않는다. 비밀값은 환경 변수로 관리하고 이름만 문서에 적는다.

공통 잠금·서버 시각·오류 계약·DB 테스트 기준은 [분해 계획](../spec-plan.md)의 공통 구현·검증 계약을 따른다. 참여자 인증이 필요한 경계에서는 서버가 약속 소속·세션·현재 역할·상태를 검사한다. 공개 링크 안내와 외부 챗봇은 각 경계의 공개 범위·호출 검증을 적용한다. 다른 참여자의 민감 정보를 오류에 포함하지 않는다.

## 구현 계획

공식 규격·진입 시나리오 확인 → 실제 가능한 요청/응답 예시 확정 → 유효·실패·재시도 TDD → Route Handler → 실제 테스트 봇 왕복 검증. 예정 apps/web/src/lib/kakao/, src/app/api/kakao/skill/route.ts. 웹 독립 테스트에는 고정된 링크 fixture를 사용하며 공개 대체 생성 기능을 만들지 않는다.

한 동작의 실패 assertion을 실제 확인한 뒤 최소 구현·회귀 검증을 반복한다. 테스트 도구 오류나 DB 연결 실패는 RED로 인정하지 않는다.

## 검증 계획

- AC별 검증 경계·원본 근거는 아래 표를 따른다. 아직 테스트 파일·제품 기능을 생성하지 않았다.
- 단위 테스트 예정 명령: 프로젝트 루트에서 docker compose exec tools npm run test -- src/lib/kakao/kakao.test.ts.
- DB 통합 예정 명령: docker compose exec tools npm run test:integration -- src/lib/kakao/kakao.integration.test.ts. test:integration은 현재 없으며 001에서 분리 설정을 추가할 계획이다. DB 검증 항목이 없는 AC에 억지로 통합 테스트를 만들지 않는다.
- DB 변경이 있으면 전용 테스트 DB 보호 확인 → 로컬 마이그레이션 작성 → Client 생성 → 빈 테스트 DB에 기존 마이그레이션 적용 → 실제 제약·트랜잭션 검증 순서로 진행한다. 운영 적용은 별도 배포 요청 시 db:deploy로만 한다.
- 격리: TEST_DATABASE_URL과 테스트 DB 이름·로컬 호스트 허용 목록을 검사하고 개발·운영 URL을 거절한다. 동시성은 독립 연결과 동시 시작 장벽을 사용한다. 상세 구성은 분해 계획에 정의한다.
- 브라우저 동작·오류 복구·모바일을 실제 확인한다. 이미지가 있는 요소는 원본 1280×3042 참고 시트를 사용한다. 제품 화면 검수 크기는 390×844와 1280×800을 제안하며 디자인 원본 크기로 주장하지 않는다.
- 최종 검증: 관련 단위·DB·브라우저 회귀, Docker Node.js 24의 npm run lint, npm run typecheck, npm run build. 필요한 검증을 실행하지 못하면 미검증으로 남긴다.
