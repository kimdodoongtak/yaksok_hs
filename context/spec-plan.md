# 약속 잡기 도우미 — MVP 기능 스펙 분해 계획

## 기준 자료와 분석 범위

- 상태: 초안 / 일부 확인 필요. 최초 자료 확인·스펙 작성 2026-11-05, 대응표·문서 점검 정리 2026-11-06.
- 입력은 context/inputs/의 하위 자료 전체다. 발견한 제품 자료 3개와 안내 README 1개를 읽었다. 숨김·무시 파일, 비밀 설정, node_modules·빌드 산출물은 요구사항 분석에서 제외한다.
- PRD·ERD 본문 전체, PNG 시트 전체를 확인했다. 별도 비즈니스 규칙·API 문서는 사용자가 작성했지만 미제공이다. 현재 제공 자료의 분석이며 미제공 자료까지 분석했다고 주장하지 않는다.
- Figma 원본 링크·file key·node ID는 제공되지 않았다. 이미지에서 확인한 8개 컴포넌트만 시각 근거로 사용하며 MCP 조회를 하지 않았다.
- 2026-11-05 사용자 결정: PRD와 ERD가 충돌하면 ERD를 우선한다. 비충돌 PRD 요구사항은 유지한다. 미제공 규칙 문서의 내용을 추정하지 않는다.
- 범위: 챗봇 링크 발급부터 비회원 참여·시간 조율·추천·방장 확정·공유 및 재조율·탈퇴·취소까지의 MVP. 장소·회원·알림 확장은 이후 범위다.
- 앱은 설정·빈 Prisma 스키마만 있고 src 앱·제품 테스트·마이그레이션은 아직 없다. 초기화는 기존 000을 재사용한다. 현재 기능은 대기이며 이 작업에서 변경하지 않는다.
- Next.js 16 / TypeScript 5 / Node.js 24 / Prisma 7 / Tailwind CSS 4, Vercel + Neon, 로컬 Docker PostgreSQL 17 기준을 유지한다.

## 먼저 검토할 내용

1. 아래 10개 제품 기능이 원하는 MVP 범위인지 검토한다. ERD로 해소된 정원·수동 확정·자동 삭제 여부는 다시 결정할 필요가 없다.
2. 전체 정책을 지금 한꺼번에 확정할 필요는 없다. 앱 초기화 000은 독립적으로 진행 가능하며 001의 OPEN-01·03·04는 2026-11-13 사용자 결정으로 해당 범위에서 확정했다. 이후 기능에서는 남은 OPEN 항목을 정한다.
3. 기존 비즈니스 규칙·API를 정리해서 다시 제출하는 것은 필수가 아니다. 현재 자료에서 빠진 항목은 아래 질문에 답하거나 기능별 초안에서 제안을 검토하면 된다.
4. Figma 전체 화면이 없어도 화면안을 만들 수 있다. 현재 이미지에 없는 화면·모바일 배치는 새 설계 제안으로 검수한다.

## 공통 구현·검증 계약

아래 함수명·응답·파일 배치는 이번 초안의 기술 제안이다. 미제공 API 문서의 기존 계약이나 이미 구현한 코드로 주장하지 않는다.

### 데이터와 권한

- 001: 링크·약속·참여자·세션과 공통 제약 도입. 004: 슬롯 테이블 도입. 005: 후보 계산 결과는 저장하지 않음. 이후 기능은 기존 구조를 사용하며 새 모델은 근거가 있을 때만 추가한다.
- UUID PK/FK, Timestamptz(3) 시점, Date 일자, 일일 분 경계를 사용한다. DB 제약·잠금·공개 서비스 검증을 함께 적용한다.
- role=host 조건부 UNIQUE는 최대 한 명만 보장한다. 취소되지 않은 약속의 active host 정확히 한 명은 생성·승계 트랜잭션으로 지킨다.
- 모든 자식 변경도 약속 행 잠금 규칙에 참여한다. 생성/초안 정리는 링크→약속 순서, 그 외 약속 변경은 약속부터 잠그고 최신 상태·권한을 읽는다. 후속 코드에 잠금 순서를 역전시키지 않는다.
- 잠금 후 실제 서버/DB 시각으로 마감을 판정한다. 대기 전에 얻은 시각으로 늦은 제출을 허용하지 않는다. 주입 가능한 시각으로 경계를 검증한다.
- 기한이 지난 collecting을 발견한 쓰기 경계는 closed 전환과 해당 요청의 상태별 허용 여부를 구분한다. 모집 중에만 가능한 변경은 거절하되 closed 전환은 커밋한다. closed에서 허용되는 탈퇴·확정·재조율 등은 각 스펙의 최신 상태 규칙에 따라 처리한다. 오류를 던져 상태 전환까지 롤백하는 구현을 피한다.
- GET은 읽기만 수행한다. effectiveStatus·draft 만료 여부를 계산하되 데이터 정리는 쓰기에서만 한다.
- 2026-11-13 사용자 결정: 초대 링크 만료는 유효 세션보다 우선한다. 기존 방장·참여자도 서버 조회·변경·재인증을 차단하며 화면에는 “만료된 약속입니다”만 표시한다. 후속 기능도 같은 만료 판정을 사용하고 상세·참여자·결과를 노출하지 않는다.
- 2026-11-14 사용자 결정: 유효한 링크의 취소된 약속은 인증 부재·세션 만료보다 취소 오류를 우선한다. 로그인 없이 “취소된 약속입니다”만 표시하고 상세·참여자 정보는 공개하지 않는다. 링크 자체가 만료됐다면 기존 만료 안내가 우선한다. 상세 상태표는 003 스펙에 있다.
- 참여자 인증이 필요한 요청은 세션의 약속·active·최신 역할을 검증한다. 공개 링크 안내와 외부 챗봇 호출에는 각 경계의 최소 공개·호출 검증 정책을 적용한다.
- Server Action은 성공 데이터 또는 구조화된 도메인 오류를 반환한다. ERD의 401·409·422는 HTTP 계약이 있는 Route Handler에 매핑하며 Action의 HTTP 응답 코드로 기계적으로 복사하지 않는다.
- 서버 컴포넌트는 데이터 계층을 직접 호출한다. 폴링은 읽기 전용 Route Handler를 제안한다. 비밀값·해시·원시 DB 오류·다른 참여자의 제출 여부를 응답하지 않는다.

### 격리된 DB 검증 계획

현재 구성에는 테스트 전용 DB·test:integration 명령이 없다. 001에서 아래 구성을 추가하고 실제 명령을 docs/local-development.md에 반영할 계획이다.

1. 로컬 Docker PostgreSQL에 개발 DB sdd와 분리된 sdd_test 및 테스트 전용 권한을 준비한다. 개발 DB를 초기화하거나 테스트에 재사용하지 않는다. 별도 Compose 프로젝트를 선택해도 동등한 격리를 문서화한다.
2. 테스트 연결 변수는 TEST_DATABASE_URL로 분리한다. 도우미가 로컬 허용 호스트·정확한 DB 이름·실제 current_database()를 확인하고 DATABASE_URL·DIRECT_URL의 개발/운영 대상을 테스트 용도로 받지 않는다. 허용 대상 확인 전 마이그레이션·쓰기·정리를 거절한다. 연결 문자열은 출력하지 않는다.
3. Prisma 마이그레이션은 개발 스키마 변경 절차로 작성하고, 보호된 테스트 실행기가 테스트 대상에만 기존 마이그레이션을 적용한다. 배포 명령을 테스트 환경 변수만 바꿔 무심코 호출하지 않도록 명시적으로 분리한다.
4. Vitest 단위 설정에서 integration 파일을 분리하고 apps/web/package.json에 test:integration을 추가한다. 테스트 DB·설정이 없으면 명확히 실패시키며 빈 성공·skip으로 숨기지 않는다.
5. 각 사례에 고유 데이터를 사용한다. 독립 연결·트랜잭션과 동시 시작 장벽으로 실제 경쟁을 재현한다. 정상·실패 건수, 최종 행 수·상태·세션·버전을 함께 확인한다.
6. 정리는 확인된 테스트 DB의 해당 테스트 데이터만 FK 역순으로 수행한다. 전체 데이터 초기화가 필요하면 전용 대상임을 재검사한다. 원자성 검증을 위한 전체 롤백과 동시 요청 검증을 구분한다.

예정 실행 명령은 각 스펙에 기록했다. 001 구현 후 확정될 명령이며 현재 실행 가능·통과 상태가 아니다. 앱 소스·DB 스키마·패키지·테스트 설정은 모두 apps/web/ 아래에 둔다.
