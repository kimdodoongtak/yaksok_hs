## R1 · P2 · 오래된 설정 화면의 영향 안내와 실제 제출 초기화가 다름

- 위치: `apps/web/src/components/promise-settings/rescheduling-form.tsx:19`, `:28`, `:35`, `:48`. 저장 경계는 `apps/web/src/lib/rescheduling/service.ts:49`와 `:65`.
- 화면은 최초 `initial.settings`만으로 영향 안내를 계산한다. 편집 화면에 최신 설정 갱신이나 안내 기준 확인이 없고, 서버는 잠금 뒤 최신 DB 범위와 비교해 저장한다. 두 탭의 기준이 달라져도 상태가 collecting이면 요청이 성공한다.
- 재현: 방장이 하루 09:00~18:00인 설정을 A/B 두 탭에서 연다. B에서 종료를 17:30으로 줄여 저장한다. A에서는 소요 시간만 60→90분으로 바꾸고 저장한다.
- 실제 일회성 Chromium/격리 PostgreSQL 확인 결과: B 저장 뒤 제출 완료 2명 유지 → A 확인 창은 **“기존 선택과 제출 상태는 유지돼요.”** → A 저장 뒤 제출 완료 **0명**, 하루 종료는 다시 18:00, 소요 시간 90분. 서버에서는 최신 17:30 대비 18:00 확대이므로 전체 제출 초기화가 실행된다.
- 영향: 방장이 재제출 필요를 안내받지 못한 채 기존 응답이 전체 히트맵·후보 집계에서 제외된다. 서버의 최신 상태 순차 적용 자체는 AC-6과 일치하지만 사용자 흐름의 변경 영향 확인과 AC-7 동기화가 충분하지 않다.
- 보완 방향: 최신 설정에 근거한 영향을 확인하고, 확인 이후 저장 사이에 기준이 달라졌을 때도 잘못된 보존 안내로 저장되지 않도록 재확인 경계를 둔다. 전용 설정 버전 컬럼 없이 처리하고 기존 AC-6 정책과 일관성을 유지한다.
- 다음 구현: 두 탭 시나리오의 실패 테스트를 먼저 남긴 뒤 수정한다. 안내를 띄운 뒤 다른 탭이 바꾸는 경우도 확인한다. 이번 일회성 재현은 결함 확인 근거이며 수정의 RED/GREEN으로 소급하지 않는다.

## TDD·경계·검증

- 기존 TDD 기록의 실제 RED→GREEN과 사후 검증을 구분해 확인했다. 범위 판정·권한·상태 전환·축소·확대·재제출 안내의 실패 근거가 있고 mock DB로 실제 트랜잭션을 대신하지 않았다.
- 007 DB 통합 테스트 9개를 이번 검토에서 Docker Node.js 24로 재실행해 종료 0을 확인했다. 기존 테스트에는 R1의 오래된 편집 화면 시나리오가 없다.
- R1은 `scripts/browser-server.mjs`로 격리 `sdd_test`를 사용하는 서버를 띄우고, stdin 일회성 Node/Playwright 스크립트로 두 탭의 실제 조작·화면 문구·DB 결과를 대조해 재현했다. 테스트 대상 보호 확인, 생성 데이터 정리, 테스트 서버 종료를 수행했다. 개발 DB/운영 DB는 변경하지 않았다.

- 서버 전용 모듈과 클라이언트 타입 참조를 구분하며 PIN·세션 정보의 신규 노출이나 의존성·스키마 추가는 발견하지 못했다.

- 후속 `$feature 시작` 요청으로 구현했다. 서버가 잠금 안에서 `confirmedImpact`(범위 영향)·`confirmedClear`(확정 해제 확인)를 최신 실제 영향과 비교한다. 다르면 `IMPACT_CHANGED`를 반환해 응답·설정·확정 저장을 중단한다.

- 실제 RED→GREEN: 범위 영향 불일치 DB, 두 탭 변경이 확인 창 이전/이후인 브라우저, 확정 해제 안내 불일치 DB. 실행 기록은 [007 TDD](../tdd/007-rescheduling.md)에 추가했다.
- 보완 후 007 DB 11개·관련 Chromium 14개·전체 단위 23개·린트·타입 검사·운영 빌드 통과. 제품 완료 처리는 하지 않으며 정식 재검토가 다음 단계다.
