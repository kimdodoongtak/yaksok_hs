# 모바일 시간표 스크롤·선택 전환 검토

- 날짜: 2026-11-20
- 스펙: [모바일 전환](../features/mobile-calendar-mode-spec.md)
- 실행 근거: [TDD 기록](../tdd/mobile-calendar-mode.md)

## 원인과 변경

시간 칸의 `pointerdown`에서 즉시 선택을 시작하고 `touch-action: none`으로 브라우저 스크롤을 막고 있었다. 바깥 여백 확보는 시간 칸 위에서 시작하는 스크롤 의도를 처리하지 못한다.

터치 입력은 기본 스크롤로 두고 고정 도움말 영역에 명시적 전환 버튼을 넣었다. 기본 터치 입력은 드래그 처리기로 넘기지 않고 `pan-y`를 사용한다. 선택 상태에서만 기존 드래그와 자동 스크롤을 사용한다. 마우스·키보드 입력, 선택값과 편집 이력, 서버 제출 계약은 유지한다.

첫 터치를 활성화로 소비하는 방식은 아직 적용하지 않았다. 사용자가 두 방식의 사용성을 비교 중이며 우선 버튼 방식을 적용해 확인하는 범위다.

## 수용 기준 검토

| AC | 검토 결과 | 근거 |
| --- | --- | --- |
| 1 | 충족 | 320·393px 기본 탭·시간 칸 위 스와이프 RED→GREEN |
| 2 | 충족 | 버튼 전환 RED→GREEN, 기존 손가락 드래그·해제·취소·자동 스크롤 회귀 |
| 3 | 충족 | 전환 후 되돌리기·복구, 제출/다른 보기 뒤 스크롤 복귀 RED→GREEN |
| 4 | 충족 | 내 시간·모집 중에만 버튼 렌더링, 전체 시간에서 숨김 확인. PC 입력 회귀 |
| 5 | 충족 | 320·393px 네 행·가로 넘침·고정 버튼 검사와 실제 캡처 검수 |

DB 스키마·데이터 정책·의존성 변경은 없다. 새 테스트는 서버 계산을 대역으로 만들지 않고 격리 DB fixture의 실제 화면을 조작한다. 기존 터치 테스트에는 사용자 동작에 추가된 선택 모드 진입만 반영했다.

실제 휴대전화 Safari·카카오톡 WebView 사용감과 운영 반영은 미검증이다. 최종 명령 결과는 TDD 기록을 따른다.
