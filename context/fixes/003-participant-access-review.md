## 발견사항

### R1 · P3 · 정원 도달 시 로그인 폼과 탭 선택 상태가 달라짐

- 위치: `apps/web/src/components/participant-access/access-panel.tsx:49`, `:65`, `:67`.
- 조건: registration=open에서 기본 “처음 참여” 모드로 화면을 열고, 다른 참여자로 정원이 채워진 상태가 5초 폴링으로 전달됨.
- 실제: “처음 참여” 탭은 없어지고 “로그인하기” 폼은 표시되지만 유일한 “다시 로그인” 탭은 `aria-pressed=false`로 남아 선택 강조가 없다. 내부 mode는 최초 join을 유지하고 폼만 registration에 따라 login=true를 사용한다.
- 기대: 실제 로그인 폼과 선택 탭이 동일한 유효 모드를 사용해야 한다. 모집 마감으로 open→closed가 되는 경우도 같은 조건식의 영향을 받는다(이번 실제 재현은 open→full).
- 재현: 임시 Node/Playwright 스크립트로 허용된 sdd_test에 정원 2명·방장 1명의 약속을 생성하고 393×852에서 접속했다. DB에 마지막 참여자를 추가한 뒤 정원 안내를 기다렸다. 출력은 `loginFormVisible:true`, `loginTabSelected:"false"`, `joinTabCount:0`. 종료 코드 0, fixture 및 임시 서버 정리 완료.
- 이미지: `apps/web/test-results/review-003-capacity-transition.png` 직접 확인.
- 영향: 로그인 처리나 서버 정원 차단 우회는 아니다. 화면의 선택 상태와 보조 기술에 전달하는 상태가 잘못된다.
- 후속: 상태 변경 후 탭과 폼의 모드를 함께 계산하도록 보완하고, 기존 화면을 열어 둔 상태에서 정원 도달·마감 전환을 다루는 브라우저 회귀를 추가한다. 이번은 검토 재현이며 제품 수정 전후 RED/GREEN을 완료했다고 기록하지 않는다.

## 테스트·구조 검토

- TDD 기록의 초기 실제 RED/GREEN과 이후 처음부터 통과한 사후 회귀를 구분했다. DB 동시성은 독립 Prisma 연결·장벽을 사용하고, 저장 실패는 실제 PostgreSQL 트리거로 롤백을 확인한다.
- 통합 테스트의 해시 대역은 도메인·경계 검증용이며 실제 scrypt는 기존 단위·브라우저 검증 근거가 별도로 있다. 테스트 skip/todo는 없고 DB 대역으로 제약·원자성을 대체하지 않았다.
- 서버 전용 서비스와 런타임을 확인했다. 클라이언트 DTO에 PIN·해시·세션 토큰을 전달하지 않으며 변경 Action은 서버 쿠키로 약속 소속을 검증한다. 상태 응답은 private/no-store 및 Vary: Cookie다.
- 보안 카운터 PK·만료 인덱스·마이그레이션을 확인했다. promise FK의 CASCADE는 신규 보안 카운터 정리용이고 기존 제품 도메인 FK의 RESTRICT를 변경하지 않는다.
- 신규 의존성 추가 없음. 004 시간 제출·008 탈퇴·009 취소 실행은 미구현 범위로 구분하고 결함으로 세지 않았다.
- 문서 정리 필요: spec-plan.md의 OPEN-02·03·09·10 및 FLOW-006 일부 셀은 여전히 “구현 전”이다. 현재 구현 기록과 맞춰 후속 정리할 항목이며 제품 정책 미정으로 해석하지 않는다.
