# TDD 개발 규칙

이 문서는 기능 구현과 버그 수정의 공통 기준이다. 제품 동작의 기준은 승인된 기능 스펙과 원본 자료이며, 테스트는 그 기준을 실행 가능한 형태로 확인한다.

## 적용 범위

- 필수: 입력 검증, 권한, 상태 전환, 시간·정원 경계, 후보 계산, 저장 충돌, 데이터 변경 및 버그 수정.
- 규칙 계산은 공개 함수·서비스 경계의 단위 테스트로, DB 제약·트랜잭션·동시 요청은 실제 격리된 PostgreSQL의 통합 테스트로 확인한다.
- 사용자 흐름의 연결은 필요한 E2E 테스트로 보완한다. 피그마와의 색상·간격·반응형 일치는 실제 화면으로 별도 검수한다.
- 정적 문서·스타일·초기 환경 구성처럼 의미 있는 제품 동작이 없는 변경은 TDD 비대상으로 정하고 이유와 대체 검증을 기록한다. 모든 파일에 억지로 테스트를 만들지 않는다.
- UI 테스트 환경과 E2E 도구는 아직 설치되어 있지 않다. 필요할 때 해당 기능 스펙에서 도구·검증 범위를 정하고 설정한다.

## 시작 전

1. 원본 규칙 → 스펙의 AC(수용 기준) → 관찰할 결과 → 테스트 파일·명령을 연결한다. 이미 합의한 기준을 반복 확인하지 않는다.
2. 테스트할 공개 경계와 최소 시나리오를 정한다. 입력·기대값은 명세나 독립적으로 계산한 예시에서 가져오고 구현 코드에서 복제하지 않는다.
3. 기존 변경과 테스트 상태를 확인한다. 제품 동작이 아직 없어서 테스트가 없으면 그대로 기록한다.
4. 구현을 막는 정책 모순만 확인한다. 확정되지 않은 제품 동작을 테스트로 먼저 고정하지 않는다.
5. `context/tdd/_template.md`를 복사해 기능별 기록 `context/tdd/<스펙-ID>.md`를 만든다. 기존 기록은 이어 쓰며 `current-feature.md`에는 그 경로만 연결한다.

## 동작 하나씩 RED → GREEN → REFACTOR

### RED: 의도한 실패 확인

- 하나의 관찰 가능한 동작에 대해 테스트를 먼저 작성한다. 구현을 시작하기 전에 그 테스트를 실제로 실행한다.
- 기대한 동작이 아직 없거나 잘못되어 실패하는지 확인하고 명령·종료 코드·핵심 실패 메시지를 기록한다.
- 테스트 수집 실패, 의존성 누락, 오타, DB 접속 실패, 환경 변수 누락은 유효한 RED가 아니다. 먼저 실행 환경을 고친다.
- 필요한 경우 동작이 없는 최소 인터페이스 스텁만 만든 뒤, 동작 검증 assertion이 실패하게 한다. 제품 동작 구현은 RED 이후에 한다.
- 새 테스트가 처음부터 통과하면 기존 구현으로 이미 충족되는지 확인한다. 이를 RED를 거친 TDD라고 기록하지 않는다. 누락된 다른 동작 또는 다음 시나리오로 진행한다.

### GREEN: 필요한 만큼 구현

- 현재 실패 테스트를 통과시킬 최소 구현을 한다. 아직 명세에 없는 기능이나 미래 테스트를 예상해 구현하지 않는다.
- 같은 테스트를 다시 실행하고, 영향을 받는 기존 테스트도 실행한다. 통과 명령·종료 코드·결과를 기록한다.
- 실패를 숨기기 위한 테스트 삭제, `skip`·`todo` 전환, assertion 약화, 대상 로직 자체의 mock, 빈 테스트 성공 설정을 금지한다.
- 테스트 기대값이 명세와 다르다면 근거를 확인하고 잘못된 테스트를 수정한다. 제품 규칙 변경이 필요하면 결정과 스펙을 먼저 갱신한다.

### REFACTOR: 통과 상태에서 정리

- 중복·이름·구조를 해당 기능 범위 안에서 정리하고 관련 테스트를 다시 실행한다. 무관한 리팩터링으로 범위를 넓히지 않는다.
- 다음 동작의 RED로 이동한다. 기능 전체의 테스트를 한꺼번에 쓴 뒤 구현을 몰아서 하지 않는다.

## DB·시간·외부 서비스

- DB 대역은 로직 단위 테스트에 사용할 수 있지만 제약조건·잠금·트랜잭션·동시성 검증을 대체하지 못한다.
- 현재 Compose의 `db`는 개발 DB다. 데이터 삭제·초기화가 필요한 통합 테스트는 별도 테스트 DB 또는 별도 Compose 프로젝트·볼륨에서 실행한다.
- 실제 DB 테스트를 추가하는 스펙에 전용 연결 변수, 대상 DB 확인, 마이그레이션, 데이터 격리·정리, 실행 명령을 포함한다. 테스트 도우미는 허용된 테스트 DB가 아니면 쓰기를 거절하도록 만든다.
- 개발·미리보기·운영 데이터를 임의 초기화하지 않는다. Neon 운영 DB에 테스트를 실행하지 않는다. 연결 문자열이나 비밀값을 기록하지 않는다.
- 동시성 테스트는 독립 연결·트랜잭션과 동시 시작 조건을 사용하고 성공 건수·최종 상태를 함께 확인한다. 단순 순차 호출로 경쟁 상황을 검증했다고 주장하지 않는다.
- 시간 경계는 고정하거나 주입한 시각으로 재현한다. 의미 없는 대기 시간으로 테스트를 통과시키지 않는다.
- 외부 API 대역은 외부 경계에서 사용하고, 실제 계약·응답 형식의 검증 여부는 별도로 기록한다.

## 기존 코드와 버그

- 버그 수정은 먼저 문제를 재현하는 실패 테스트를 만들고 원인 수정 후 통과를 확인한다.
- 이미 구현된 코드에 뒤늦게 추가한 테스트는 '기존 동작 검증/사후 테스트'로 기록한다. 구현이 없는 것처럼 과거 RED를 만들어내지 않는다.
- 테스트만 통과해도 원본 요구사항을 잘못 반영했다면 미완료다. 리뷰에서 명세와 기대값을 대조한다.

## 완료 조건

- TDD 대상 AC에 실제 RED·GREEN 근거가 있고 관련 회귀 테스트가 통과했다.
- 비대상 AC는 이유와 실제 대체 검증 결과가 있다. 기존 동작 검증은 사후 테스트임을 구분했다.
- 코드 정리 후 필요한 테스트·린트·타입 검사·빌드·실제 DB·브라우저 검증을 수행했다.
- 필수 검증이 실패했거나 실행되지 않았다면 완료 처리하지 않는다. 환경 문제는 '차단/미검증'으로 남긴다.
- 로그에는 짧은 핵심 결과만 남기고 비밀값·개인정보는 제외한다. 문서 체크만으로 테스트 실행을 대신하지 않는다.

실행 예시는 [TDD 사용 가이드](../docs/tdd-guide.md)를 따른다. 이 정책은 에이전트의 작업 지침이며 자동으로 TDD 순서를 강제하는 프로그램은 아니다.
