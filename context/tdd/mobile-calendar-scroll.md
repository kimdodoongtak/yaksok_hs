## 실행 기록

- RED: `docker compose exec -T tools npm run test:browser -- e2e/availability.spec.ts --grep '오른쪽 하단'`, 종료 코드 1. 두 화면 모두 스크롤 제스처 후 기존 09:00 선택 외에 09:30·10:00·10:30·11:00 네 칸이 추가돼 선택 유지 assertion 실패. 환경 오류가 아닌 사용자 문제를 재현했다.
- 최소 구현: 모바일 시간표·날짜 열의 오른쪽에 28px 여백을 함께 확보한다. 화면 자체의 여백을 합하면 320px에서 40px, 393px에서 44px로, 이곳에서 시작한 터치는 선택 버튼에 닿지 않고 기본 페이지 스크롤이 된다. 도움말을 양옆 여백 안내로 수정한다.
- 첫 검증: 오른쪽 스크롤·선택 유지와 기존 모바일/PC 3개 동작은 통과했다. 추가 배치 assertion은 기존 셀의 양옆 여백을 무시하고 날짜·셀의 좌측 좌표 일치를 요구해 2px 차이로 실패했다. 열 정렬 기준에 맞게 날짜·셀 중심 좌표 비교로 바로잡았으며, 스크롤·선택 유지 assertion은 그대로 유지했다.
- 관련 전체 회귀 중 기존 손가락 드래그 테스트에서 시간축 스크롤 후 다음 시나리오를 위해 `scrollTo(0,0)`으로 초기화하는 단계가 85px에서 실패했다. 브라우저 기본 관성 스크롤이 초기화와 겹치는 테스트 준비 문제로, 시간축을 탭해 관성을 멈춘 뒤 위치를 초기화하도록 보완했다. 스크롤·선택·제출 assertion은 유지한다.
- 같은 회귀에서 320px·2시간 보기의 후보 시간 캡션이 좁아진 칸에서 줄바꿈되어 후보 영역 위로 0.5px 벗어났다. 기존 후보 영역 경계 assertion은 그대로 유지하고, 359px 이하 읽기 전용 칸의 좌우 여백을 3px→1px로 줄여 가독성을 확보한다. 전체 44개 중 42개 통과, 위 두 항목 보완 후 재검증한다.
- 집중 재검증에서 모바일 터치 3개는 통과했고 후보 캡션은 여백 조정만으로 해결되지 않았다. DOM 측정으로 `10–12`가 실제 두 줄(23px)이 되는 것을 확인했다. 359px 이하에서 정시 범위를 한 줄로 표시하고 자간을 -.04em로 조정한다. 임시 진단 코드는 제거했다.

- 추가 시각 교정: 모바일 응답 마감의 검정 캡슐을 제거하고 보조 텍스트 액션으로 표시한다. 기능은 바꾸지 않으며 터치 높이 44px와 확인창을 유지한다.

- 기존 왼쪽 시간축 테스트의 다음 시나리오 준비가 관성 때문에 10px에서 실패했다. 탭으로 관성을 끊는 기존 보완 대신 CDP의 실제 터치 스크롤에서 `preventFling`을 지정해 제스처 종료를 동기화한다. 제품의 관성 동작 및 스크롤·선택·제출 assertion은 그대로다.
- 마감 후 후보 보기 링크는 사용자 추가 요청에 따라 빨간 텍스트로 표시하고 실제 화면 캡처로 확인한다.
- 시간축 테스트 정리: `synthesizeScrollGesture`는 이 테스트에서 스크롤을 재현하지 못해 실패했다. 원래의 실제 touchStart/Move/End 이벤트로 복원하고, 관성이 남는 시간축 스크롤과 드래그 자동 스크롤을 별도 브라우저 시나리오로 분리했다. 두 제품 동작의 기존 assertion은 모두 보존하며, 다음 시나리오를 위한 인위적인 `scrollTo(0,0)` 준비 단계만 제거한다.
